# 02 — static-web-server

*State observed on 8 September 2026, version **2.44.0**. The behaviours marked
"measured" were measured on `ghcr.io/static-web-server/static-web-server:2` with the
exact flags of `deploy/steps/60-app.sh`, not read off the documentation.*

---

## What it is

[static-web-server](https://static-web-server.net/) (SWS), by Jose Quintana: a static
file server written in Rust, asynchronous, distributed as a **single dependency-free
binary**. Licensed MIT/Apache-2.0.

Why this one rather than nginx or Caddy: the image is **8.4 MB in two layers** and
contains nothing but the binary. No shell, no package manager, no configuration file to
watch. On a shared machine where we are tenants, the easiest surface to defend is the
one that does not exist.

---

## How the container is organised

### The base image

```
ghcr.io/static-web-server/static-web-server:2
├─ Entrypoint : ["/static-web-server"]
├─ Cmd        : (none)
├─ User       : (empty)
├─ Expose     : 80/tcp
├─ WorkingDir : /
├─ Layers     : 2
└─ Size       : 8,380,351 bytes
```

Two practical consequences follow from that table.

**The `Entrypoint` is the binary itself**, with no `Cmd`. Everything after the image
name in `docker run` is therefore passed **straight to the server** as command-line
arguments. That explains the shape of our launch, which looks like nothing and is not
innocuous:

```bash
docker run -d --name guyana-site ... aurora-site \
  --root=/public --port=80 --page-fallback=/public/index.html \
  --compression=true --cache-control-headers=false
```

There is no configuration file in our setup: **the configuration is the command line**,
and it reads in full in `60-app.sh`.

**There is no shell in the image.** `docker exec guyana-site sh` fails, and even `id`
does not exist. So the running container cannot be inspected from the inside:
diagnosis goes through `docker logs`, through `docker inspect`, or by querying the
server over HTTP. That is a real operating cost, and the counterpart of the reduced
surface.

> **`User` is empty: the process runs as root inside the container.** The publisher also
> ships *rootless* variants (user `sws`, public root `/home/sws/public`) which we do not
> use. That is not free; it is partly offset by `--read-only`, `--security-opt
> no-new-privileges:true`, the absence of a shell and the absence of a published port.

### Our image

The Dockerfile is two lines, generated by the launcher:

```dockerfile
FROM ghcr.io/static-web-server/static-web-server:2
COPY public/ /public/
```

`public/` is Hugo's output, built on the control post. The build context leaves over
`stdin`: nothing is written on kubb.

> **The `:2` tag is mobile.** Today it designates 2.44.0; tomorrow it will designate
> 2.45. What runs can therefore change without a single line of the repository changing.
> `DB_IMAGE` is pinned by `sha256:`; this one is not.

### The hardening, and where it comes from

| Measure | Set by |
|---|---|
| `--read-only` + `--tmpfs /tmp` | `docker run` |
| `--security-opt no-new-privileges:true` | `docker run` |
| no published port | `docker run`, **and verified** afterwards |
| `--restart unless-stopped` | `docker run` |
| TLS, security headers, authentication | **Traefik**, not SWS |

In this setup the static server does nothing but serve bytes. Everything to do with
transport and access security is delegated to the proxy — see note
[01](01_hosting-and-routing.md).

## What SWS can do

### What we use

| Option | Value | Why |
|---|---|---|
| `--root` | `/public` | the root served |
| `--port` | `80` | Traefik reaches the container by name on the `proxy` network |
| `--page-fallback` | `/public/index.html` | client-side routing: any unknown URL returns the home page |
| `--compression` | `true` | gzip/brotli/zstd/deflate on the fly |
| `--cache-control-headers` | **`false`** | so that Traefik is the **sole** emitter of `Cache-Control` |

### What we do not use, and why

| Option | What it would do | Why not here |
|---|---|---|
| `--basic-auth` | plain HTTP authentication | Traefik authenticates, and it alone can set `X-Webauth-User` |
| `--security-headers` | sets a set of security headers | same rule: one emitter per header |
| `--cors-allow-origins` | CORS | the site is called by itself only |
| `--health` | a `/health` endpoint | Traefik does not use it in this setup |
| `--metrics` | Prometheus export | no collection on kubb |
| `--directory-listing` | directory index | would expose the tree |
| `--page404`, `--page50x` | error pages | `--page-fallback` short-circuits them |
| `--http2`, `--https-redirect` | TLS terminated by SWS | Traefik terminates TLS |
| `--maintenance-mode` | deliberate 503 | never had a use for it |
| `--disable-symlinks` | refuses to follow links | the image contains none |
| `--ignore-hidden-files` | dotfiles | **left at the default, which refuses them — see "two measured behaviours" below** |

### Advanced configuration, through a TOML file

Beyond the command line, SWS accepts `--config-file=/path/sws.toml`, which **alone**
gives access to four mechanisms. We use none of them today.

**Virtual hosts** — a different root per `Host` header:

```toml
root = "/public"

[advanced]
[[advanced.virtual-hosts]]
host = "other.example.com"
root = "/other-root"
```

**Headers by pattern** — `[[advanced.headers]]`, with a glob `source`.

**Internal rewrites** — `[[advanced.rewrites]]`, `source`/`destination`, with capture
groups; they can target an "internal" virtual host in order to expose another root.

**Redirects** — `[[advanced.redirects]]`, with `host`, `source`, `destination` and
`kind` (301/302).

> Moving to the TOML file changes the nature of the setup: the configuration stops being
> readable in `60-app.sh` and becomes one more file to copy into the image, to version
> and to keep up to date. That is not a matter of form — it is one more configuration
> item.

## Two measured behaviours that come as a surprise

### 1. Hidden files are refused by default

**SWS ignores dotfiles**, answers 404, and leaves them out of indexes. It is a security
choice by the publisher, and it applies to **directories** as much as to files:
`.well-known/` is therefore invisible.

Measured on our image, with our flags:

```
GET /.well-known/did.json   ->  200   content-type: text/html   (body = index.html)
GET /engine/taxonomy.json   ->  200   content-type: application/json
```

**The 404 cannot be seen.** `--page-fallback` turns it into a 200 carrying the home
page. Whoever asks for a hidden file does not get an error: they get HTML announced as a
success.

Natixar's DID document is not served here: it lives on the main domain, at Netlify — see
[01](01_hosting-and-routing.md). The behaviour described holds for any hidden path of
this site.

With `--ignore-hidden-files=false` added, the same call returns:

```
GET /.well-known/did.json   ->  200   content-type: application/json   (the right body)
```

A single flag. But it lifts the protection **for every dotfile under the root**, not
only for `.well-known/` — the option has no granularity. On a root generated by Hugo,
that is worth a look at what the root contains.

### 2. The server is silent

The default log level is **`error`**. The deployed container therefore writes nothing to
`docker logs` — not even the 404s. Verified: a container launched as in production, hit
on an absent URL, produces zero lines.

With `--log-level=info`, SWS writes at start-up a full summary of its effective
configuration — every option and the value retained — then one line per request:

```
INFO static_web_server::server: static-web-server 2.44.0
INFO static_web_server::log_addr: incoming request: method=GET uri=/absent
WARN static_web_server::error_page: method=GET uri=/absent status=404 error="Not Found"
```

That summary is the most direct way to know what the server believes it is doing.
Traefik's access log, for its part, is filtered on 4xx/5xx codes — and since
`--page-fallback` returns 200 for any unknown path, the site's missing URLs do not
appear there either.

## The deployment procedure

```
1. hugo                       on the control post; a failure stops everything
2. cp public/ + Dockerfile    into a temporary directory
3. tar | ssh docker build -   context over stdin, image built ON kubb
4. docker image inspect       the image present must be the one just built
5. docker rm -f + docker run  with the routing labels
6. docker inspect             no published port — verified, not assumed
7. deployments.log            date, operator, environment, commit, image id
```

The container is **recreated** at every deployment, never updated: Docker labels cannot
be modified in place, and the container holds no state.

Step 4 is an interim measure, and known to be one. The plan requires deployment by
attested digest; until the registry and the attestation chain exist, we settle for
refusing any divergence between the image requested and the one actually present on the
target.

CI (`.github/workflows/pr.yml`, job `ephemeral`) replays the same build on a runner and
queries the site, with `--page-fallback` alone — without `--compression` or
`--cache-control-headers=false`. It checks `/unknown -> 200` there, the expected
behaviour of a client-side-routed application.
